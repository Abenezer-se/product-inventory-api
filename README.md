# Product Inventory API

This is my solution for the Product Inventory challenge. It is a REST API for managing products (create, list, read, update, and delete). I built it using Go, the Chi router, sqlc, PostgreSQL, and Docker.

## What I Used

- **Go** for the API.
- **Chi (v5)** for routing and middleware.
- **PostgreSQL 16** as the database.
- **sqlc (pgx/v5)** to generate database code from SQL queries.
- **golang-migrate** for database migrations.
- **Docker and Docker Compose** to run the application.

## Project Structure

    cmd/
      api/                  Main API program
      seeder/               Program for adding sample products

    internal/
      apierror/             Standard JSON error format
      config/               Reads environment variables
      db/                   Code generated by sqlc
      products/             Handlers, service, validation, SQL queries, and tests
      server/               Router and middleware

    migrations/              Database migration files
    scripts/
      verify.ps1             Windows verification script

    api.rest                 Sample API requests

The code is organized into layers:

**Handlers -> Service -> sqlc Queries -> PostgreSQL**

Handlers manage HTTP requests, the service handles business rules and errors, and sqlc queries communicate with the database.

## How to Run with Docker

Docker is the easiest way to run the project.

First, start the application:

    docker compose up --build -d

Then add sample products:

    docker compose run --rm api /app/seeder

Open the following address in your browser:

    http://localhost:8080/healthz

You should receive:

    {"database":"up","status":"ok"}

### What Happens When Docker Starts?

1. PostgreSQL starts and waits until it is healthy.
2. The migration service creates the database tables and then stops.
3. The API starts on port 8080.

The database uses a Docker volume named `pgdata`, so your data remains available even after stopping the containers.

To stop the application:

    docker compose down

To stop the application and delete the database volume:

    docker compose down -v

**Note:** The second command permanently deletes the database data stored in the Docker volume.

## How to Run Locally Without Docker for the API

1. Copy `.env.example` to `.env`.
2. Start PostgreSQL using Docker:

       docker compose up -d db

3. Create the database tables:

       make migrate-up

4. Add sample products:

       make seed

5. Start the API:

       make run

## Database Design

The project uses a PostgreSQL table called `products`.

| Column | Type | Rules |
|---|---|---|
| id | BIGSERIAL | Primary key |
| name | VARCHAR(255) | Required, cannot be empty |
| sku | VARCHAR(64) | Required, unique, uppercase letters, numbers, and hyphens |
| description | TEXT | Optional |
| price | NUMERIC(10,2) | Required, minimum 0 |
| stock_quantity | INTEGER | Default 0, cannot be negative |
| status | VARCHAR(32) | `draft`, `active`, or `archived` |
| created_at | TIMESTAMPTZ | Defaults to current time |
| updated_at | TIMESTAMPTZ | Defaults to current time |

The database has a unique index on `sku` and an index on `status`.

I also use database CHECK constraints to protect the data, even if someone accesses the database without using the API.

### Sample Data

The seeder uses `ON CONFLICT (sku) DO NOTHING`, so running it multiple times does not create duplicate products.

## API Endpoints

The base API path is:

    /api/v1

I included sample requests for all endpoints in the `api.rest` file.

| Method | Endpoint | Success Response | Possible Errors |
|---|---|---|---|
| POST | `/products` | 201 Created | 400, 409 |
| GET | `/products` | 200 OK | 400 |
| GET | `/products/{id}` | 200 OK | 400, 404 |
| PUT | `/products/{id}` | 200 OK | 400, 404, 409 |
| PATCH | `/products/{id}` | 200 OK | 400, 404, 409 |
| DELETE | `/products/{id}` | 204 No Content | 400, 404 |
| GET | `/healthz` | 200 OK | 503 |

### Product List Query Parameters

The API supports pagination, filtering, and searching.

| Parameter | Description |
|---|---|
| `page` | Page number. Default: 1 |
| `page_size` | Number of products per page. Default: 10, maximum: 100 |
| `limit` | Alternative to `page_size` |
| `status` | Filter by `draft`, `active`, or `archived` |
| `q` | Search products by name. Supports partial and case-insensitive matching |
| `low_stock=true` | Show products with stock quantity of 5 or less |

## Error Handling

All API errors use the same JSON response format.

Example:

    {
      "error": "validation_failed",
      "message": "one or more fields are invalid",
      "details": {
        "price": "price must be greater than or equal to 0"
      }
    }

### HTTP Error Codes

| Error Code | HTTP Status | Description |
|---|---|---|
| `bad_request` | 400 | Invalid JSON, unknown field, or invalid ID |
| `validation_failed` | 400 | One or more fields have invalid values |
| `not_found` | 404 | Product or route does not exist |
| `conflict` | 409 | Product SKU already exists |
| `unsupported_media_type` | 415 | Content-Type is not `application/json` |
| `internal_error` | 500 | Unexpected server error |
| `timeout` | 504 | The request took longer than 30 seconds |

The API also handles PostgreSQL duplicate-key errors (23505) and returns a 409 Conflict response.

## Validation Rules

I implemented validation to make sure product information is correct.

- **Name:** Required, cannot be blank, maximum 255 characters.
- **SKU:** Required, uppercase letters, numbers, and hyphens, maximum 64 characters.
- **Price:** Required, between 0 and 99,999,999.99, with a maximum of two decimal places.
- **Stock quantity:** Optional, defaults to 0, and cannot be negative.
- **Status:** Must be `draft`, `active`, or `archived`. Default is `draft`.

## Middleware and Server Features

I used the following Chi middleware:

- `RequestID` - Adds a unique ID to each request.
- `RealIP` - Gets the real client IP address.
- `Logger` - Logs HTTP requests.
- `Recoverer` - Recovers from unexpected panics.
- `Timeout` - Limits requests to 30 seconds.

I also created custom middleware that only accepts `application/json` for POST, PUT, and PATCH requests.

The server supports graceful shutdown when it receives Ctrl+C.

## Docker Implementation

I used a multi-stage Dockerfile to keep the final image small.

- The first stage builds static Go binaries.
- The second stage uses a lightweight Alpine image.
- The image includes the required certificates and timezone data.
- The application runs as a non-root user with UID 10001.
- The API image includes a health check using `/healthz`.
- Docker Compose uses `depends_on` with `service_healthy` to ensure PostgreSQL is ready before the API starts.

## My Design Decisions

Here are some important decisions I made while building this project:

- **BIGSERIAL ID:** I used BIGSERIAL because it provides simple and reliable auto-incrementing IDs.
- **Database CHECK Constraints:** I added constraints to protect data integrity at the database level.
- **Status CHECK Constraint:** I used a CHECK constraint instead of a custom PostgreSQL enum because it is easier to modify later.
- **PUT and PATCH:** Both use the same handler and update only the fields included in the request.
- **Hard Delete:** DELETE permanently removes the product from the database.
- **Price Handling:** I used `float64` in Go and NUMERIC(10,2) in PostgreSQL. The API validates prices to allow only two decimal places.

## Testing

I wrote automated tests using Go's `httptest` package and a fake in-memory store.

The tests use table-driven cases to check:

- Product validation.
- HTTP status codes.
- Pagination.
- Product filtering.
- Product searching.
- Not-found errors.
- Duplicate SKU conflicts.

The products package has approximately 85% test coverage.

To run all tests:

    go test ./... -cover
